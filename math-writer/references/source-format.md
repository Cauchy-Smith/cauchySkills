# 论文源文件格式

写作手写的是 `paper/paper.md`——**内容归源文件，排版归 `build_paper.py`**。源文件里只出现内容和语义标记，不出现字体、字号、缩进。

## 一、文件结构

```markdown
---
title: 基于GM(1,1)-马尔可夫链的新能源汽车保有量预测研究
keywords: 灰色预测；马尔可夫链；保有量预测；后验差检验；灵敏度分析
school: 某某大学
team_id: 2026A12345
members: 张三，李四，王五
---

# 摘要

（摘要正文，一段或多段，800–1000 字）

# 1 问题重述
...
```

- 开头 `---` 之间是元信息，用于封面页与摘要页。
- `# 摘要` 一节会被**移到摘要页**，不会在正文重复出现；不要手动删它。

## 二、语法表

| 写法 | 渲染为 |
| --- | --- |
| `# 问题重述` | 一级标题，自动编号为 `1 问题重述`（四号黑体居中） |
| `## 问题背景` | 二级标题，自动编号 `1.1` |
| `### 参数估计` | 三级标题，自动编号 `1.1.1` |
| `# 参考文献` | 一级标题，**不编号**（同理 `附录`、`致谢`） |
| 普通段落 | 小四宋体，首行缩进 2 字符 |
| `- 条目` | 无序列表 |
| `1. 条目` | 有序列表（自动编号） |
| `**加粗**` | 加粗 |
| `$x^2$` | 行内公式 |
| `$$ ... $$` | 独立公式行，居中并自动编号 `(章-序)` |
| `$$ ... \tag{3-1}$$` | 独立公式，使用自定义编号（渲染为 `(3-1)`，括号自动补） |
| `**加粗**` / `` `行内代码` `` | 加粗 / 等宽小字号 |
| `![图题](figures/问题2-预测-图2-1.png)` | 插图 + 图题 `图<章>-<序>` |
| `![图2-1：图题](path)` | 插图 + **显式编号** `图2-1`（覆盖自动编号） |
| `表：表题` + 紧随其后的管道表 | 三线表 + 表题 `表<章>-<序>` |
| `表2-1：表题` + 紧随其后的管道表 | 三线表 + **显式编号** `表2-1` |
| `^[1]`、`^[1,3]`、`^[2-4]` | 上标引用 |
| `[1] 作者. 题名[J]. ...` | 参考文献条目（悬挂缩进），只在 `# 参考文献` 之下 |
| ```` ``` ```` 围栏代码块 | 等宽小字号代码（用于附录源程序） |

## 三、编号规则

**图与表：一律显式编号，且一律沿用编程手的编号。**

编程手在 `solving/results-report.md` 的图表清单里已经给出论文编号（`图2-1`、`表2-1`，第一个数字是小问号）。写作手照抄，不重编：

```markdown
![图2-1：GM(1,1)模型拟合与预测曲线](../solving/figures/问题2-预测-图2-1.png)

表2-1：GM(1,1)模型预测结果
| 年份 | 预测值 | 下界 | 上界 |
```

清单里没有、但论文必要的补充图/表，**编到对应小问的序号上继续递增**（清单到 图2-4，补充图就是 图2-5），同样写显式编号。**不要用自动编号**——自动编号按章走，会和小问号错位。

**公式：用自动编号**（编程手不管公式）。公式在所属一级章内从 1 开始，得到 `(5-1)`、`(5-2)`。需要指定号时写 `\tag{5-1}`，builder 会补上括号渲染成 `(5-1)`。

**标题**：一级标题按顺序自动编号；若标题已自带编号（如 `# 1 问题重述`），builder 不再重复编号。`参考文献`、`附录`、`致谢` 不编号。

**交叉引用请手写**（如「见表2-1」「如图2-1所示」），builder 不会自动替换。

## 四、公式编号与图表编号为什么不一样

图/表编号由编程手定，因为它按**小问**组织产物、文件名里就带着编号；公式没有上游编号，只能由论文按**章**生成。两者规则不同是有意的——`check_format.py` 的连续性检查按编号的第一段分组，因此同一小问的图表必须连续、不能跨小问续号。

## 五、图片路径

图片路径**相对于 `paper.md` 所在目录**解析。coder 把图落在 `solving/figures/`，写作时按相对路径引用，例如：

```markdown
![GM(1,1)模型拟合与预测曲线](../solving/figures/问题2-预测-图2-1.png)
```

路径不存在时 builder 会在正文插入红字 `[缺失图片: ...]`，`check_format.py` 不通过——这是有意的，避免图静默丢失。

## 六、公式写法

公式必须是**文本 LaTeX**，不允许贴图。支持的 LaTeX 子集见 `latex2omml.py --selftest`；不确定的写法先自测：

```bash
python scripts/latex2omml.py "\frac{\partial L}{\partial \theta}"
```

不支持的构造会报 `LatexError` 并指出命令名，而不是悄悄渲染成错的公式。常用已支持：`\frac`、`\binom`、`\sqrt[n]{}`、`\sum/\prod/\int_{}^{}`、`\lim_{}`、`x_i^2`、`\left(...\right)`、`\begin{cases}`、`\begin{pmatrix}`、`\begin{bmatrix}`、`\begin{aligned}`、希腊字母、关系符、`\hat/\bar/\vec/\tilde`、`\text{中文}`、`\mathbf`。

行内公式在正文与**表格单元格**里都用 `$...$`，builder 会一并转成 OMML。不要在正文或单元格里写 `\frac`、`\mathcal` 这类裸命令——它们会原样留在 docx 中，`check_format.py` 的「公式渲染」项会报 FAIL。

## 七、写作禁忌

- 不要在源文件中写「约」「较好」「显著提升」这类无数值支撑的表述——正文里每个数字都要能追溯到 `solving/`。
- 不要手工敲图号、表号、公式号；让 builder 编号，交叉引用时再引用它。
- 不要在摘要里放公式编号、图表或引用。
